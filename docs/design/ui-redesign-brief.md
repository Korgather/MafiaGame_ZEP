# 마피아 게임 UI 전면 재설계 브리프

> AI UI 디자이너에게 그대로 전달하는 프롬프트입니다.
> 아래 `---` 아래부터 끝까지가 전달 내용입니다.

---

당신은 ZEP 메타버스 플랫폼 위에서 돌아가는 캐주얼 마피아 게임의 UI를 전면 재설계합니다.
이 문서 하나로 충분히 작업할 수 있도록 필요한 맥락과 제약을 모두 적었습니다.
**ZEP은 일반 웹과 규칙이 다릅니다. "제약" 절을 먼저 읽고 그 안에서 설계하세요.**

## 1. 무엇을 만드는가

플레이어 4~12명이 ZEP 맵 안의 아바타로 모여 진행하는 마피아 게임입니다.
아바타가 돌아다니는 2D 게임 화면 **위에** 우리 UI가 떠 있는 구조입니다.
UI는 게임 화면을 대체하지 않습니다 — 사람들은 UI를 보면서 동시에 아바타의 위치와
움직임(누가 어디 모여 있는지, 누가 안 움직이는지)도 봅니다. **화면을 가리는 것이
이 UI의 가장 큰 실패입니다.**

한 판의 흐름:

```
대기 → 직업 배정 → 밤 → 밤 결과 → 낮 토론 → 지목 투표 → 개표
     → 최후의 반론 → 찬반 투표 → 처형/무산 → 승리 판정 → 다음 밤
```

직업은 21종(마피아·의사·경찰·군인·연인·영매·성직자·마담·건달·정치인·도굴꾼·도둑·
짐승인간·스파이·테러리스트·자경단·시민 등)이고, 밤마다 각자 한 명을 지목합니다.

톤: 어둡고 긴장감 있지만 무겁지 않은 캐주얼 추리물. 현재 팔레트는 따뜻한 다크
브라운 계열(`#14100f` 배경)에 마피아=적색 / 시민=청색 / 강조=골드입니다.
톤 자체를 바꾸는 제안은 환영하지만, 근거를 적어 주세요.

## 2. ZEP 플랫폼 제약 — 반드시 지켜야 하는 것

이 절의 항목은 취향이 아니라 물리적 제약입니다. 어기면 화면이 깨지거나 빌드가
실패합니다. 각 항목 뒤에 이 프로젝트가 실제로 겪은 실패를 적어 두었습니다.

### 2-1. 위젯은 게임 클라이언트 안의 iframe이다

UI 한 조각을 ZEP에서 "위젯"이라고 부릅니다. 서버 스크립트가
`player.showWidget(파일명, anchor, width, height)`로 띄우면, 해당 HTML 파일이
게임 화면 위에 뜨는 iframe으로 로드됩니다.

- `anchor`: `top` / `topright` / `bottom` / `bottomleft` / `center` 등 9방위
- `width`/`height`: **픽셀 정수만** 받습니다. %도 vh도 안 됩니다.

### 2-2. %를 쓰는 유일한 길은 WidgetRearrange다

픽셀만 받는 API로는 "화면의 절반"을 표현할 수 없습니다. ZEP은 이를 위해
위젯이 부모 창으로 보내는 특수 메시지를 제공합니다:

```js
window.parent.postMessage({
  type: "WidgetRearrange",
  anchor: "topright",
  width: "96%",      // 여기서는 %·px 문자열 모두 가능
  height: "46%",
  top: "-62px",      // 상단바 보정
  zIndex: 9999,
}, "*");
```

이것이 반응형을 얻는 **유일한** 통로입니다. CSS 미디어쿼리로 iframe 안쪽을
아무리 조정해도, iframe 자체의 크기는 이 메시지로만 바뀝니다.

> **실제 사고:** 예전 구조에서는 각 위젯이 뜬 뒤 스스로 rearrange를 호출해
> **가로 폭만** %로 덮었습니다. 세로는 아무도 안 덮어서 데스크톱 픽셀
> (400px)이 모바일에 그대로 남았고, 이게 화면의 85%를 UI가 덮은 직접
> 원인이었습니다. 게다가 호출 여부가 위젯 자유라 채팅과 직업 카드 2개는
> 아예 호출하지 않아 모바일 보정이 통째로 빠져 있었습니다.

**현재 구조 (유지해야 함):** 크기 결정은 서버 코드 한 곳(`layoutOf`)이 전담하고,
계산 결과를 모든 메시지에 `layout` 필드로 실어 보냅니다. 위젯 쪽 공유
스크립트가 메시지 종류와 무관하게 이를 적용합니다. **위젯은 자기 크기를
스스로 정하지 않습니다.** "위젯이 호출을 잊을" 수 있는 자리를 없앤 설계입니다.

당신이 위젯 크기를 바꾸고 싶다면 HTML이 아니라 서버 상수표를 고쳐야 합니다
(3-2 참고). 어느 값을 어떻게 바꿔야 하는지 산출물에 적어 주세요.

### 2-3. 세로 예산 — 모바일에서 게임 화면을 절반 이상 남긴다

ZEP은 모바일 접속 비중이 높습니다. 세로 850px 폰에서 400px 위젯은 화면의
절반입니다. 그래서 예산을 못 박아 두었습니다:

```
메인 위젯          ≤ 46%   (화면 높이 대비)
+ 접힌 채팅 막대     44px
─────────────────────────
게임 화면          ≥ 48%   ← 이 줄이 지켜져야 한다
```

채팅을 펼치면 채팅(34%)이 올라오므로 메인 위젯이 0.6배로 자동 축소됩니다.
둘이 동시에 제 크기로 뜨는 경우는 없습니다.

**새 화면을 제안할 때마다 모바일 세로 %를 명시하고 이 예산 안에 드는지
직접 계산해서 적어 주세요.** 예산을 넘겨야 하는 화면이 있다면 이유를 쓰세요.

예외는 하나입니다: 단계 전환 컷(`cut.html`)만 화면을 100% 덮습니다.
게임 화면을 남기지 않는 것이 목적이고, 서버가 정한 시간에 스스로 닫힙니다.

### 2-4. 외부 호스트 접근 전면 금지

CDN, 웹폰트, 외부 이미지, 아이콘 라이브러리 — 전부 금지입니다.
빌드 스크립트가 정규식으로 검사해서 **위반 시 빌드를 실패시킵니다.**

> **실제 사고:** 예전 위젯들은 imgur 10곳, cdnjs 7곳, jsdelivr 2곳에 의존했습니다.
> font-awesome은 7개 위젯에 들어 있으면서 아이콘을 **한 개도** 쓰지 않은 채
> 매번 70KB를 받았고, imgur가 죽으면 게임 화면이 통째로 비었습니다.
> 웹폰트는 도착 전까지 다른 글꼴로 그려졌다가 튀었고(FOUT), CDN이 막힌
> 사내망에서는 영영 오지 않았습니다.

그러므로:

- **글꼴**: 시스템 한글 글꼴만. 웹폰트 제안 금지.
- **아이콘**: 이모지 또는 인라인 SVG. 아이콘 폰트 금지.
- **이미지**: CSS 그라디언트·도형으로 표현하거나, 꼭 필요하면 인라인 SVG.
  래스터 이미지가 필요하면 별도로 요청하세요 (base64 인라인도 용량 때문에
  신중해야 합니다).
- **애니메이션 라이브러리**: 금지. CSS 트랜지션/키프레임만.

### 2-5. 위젯 → 부모 통신은 지정된 창구만

`window.parent`를 직접 만지는 코드는 **빌드가 거부합니다.** 공유 스크립트
`bridge.js`가 제공하는 `Parent` 객체만 씁니다:

```js
Parent.send({ type: "vote", target: 3 });   // 게임 서버로 보내기
Parent.on({ init(data) {…}, result(data) {…} });  // 서버 메시지 구독
Parent.onKey(handler);       // 게임 캔버스에 포커스 있을 때의 키 입력
Parent.grabFocus();          // 이 프레임으로 포커스 가져오기
Parent.releaseFocus();       // 게임 화면으로 포커스 되돌리기
Parent.store;                // 프레임보다 오래 사는 저장소
Parent.canReadKeys;          // 부모와 같은 출처인가
```

**포커스 규칙 (중요):** 키 이벤트는 iframe 경계를 넘지 않습니다. 위젯 안
입력창에 포커스가 있으면 WASD가 ZEP 캔버스에 도달하지 않아 아바타가 멈춥니다.
그래서 **입력을 끝낸 직후(전송·닫기) 반드시 `Parent.releaseFocus()`를 불러야
합니다.** 이걸 빠뜨리면 플레이어의 아바타가 움직이지 않습니다.

### 2-6. ZEP 자체 UI가 화면에 남아 있다

ZEP 클라이언트의 상단바와 기본 채팅 입력창은 계속 떠 있습니다.
zep-script 0.16.5에는 이를 숨기는 API가 없습니다.

- 상단바를 피하려고 기기별 오프셋을 쓰고 있습니다:
  데스크톱 `-12px` / 폰 `-62px` / 태블릿 `-40px`
- 위쪽 anchor 위젯에만 적용됩니다. 아래·가운데 위젯에 적용하면 제자리에서
  그만큼 밀려납니다.
- 우리 UI 요소가 ZEP 기본 채팅 입력창과 시각적으로 충돌하지 않아야 합니다.

### 2-7. 기기 3분기는 서버가 판정한다

`player.isMobile` / `player.isTablet`으로 서버가 판정해서 크기를 정합니다.
위젯이 `window.screen.width`로 넘겨짚지 않습니다. 현재 가로 폭:

| 기기 | 가로 |
|---|---|
| 폰 | 96% |
| 태블릿 | 60% |
| 데스크톱 | 위젯별 px (280~480) |

태블릿을 60%로 잡은 이유: 꽉 채우면 글줄이 너무 길어져 오히려 읽기 나빠집니다.

### 2-8. 접근성은 이미 지켜져 있다 — 되돌리지 말 것

> **실제 사고:** 기존 조작 요소가 전부 `<div onclick>`이었습니다. 키보드로
> 도달할 수 없고 포커스 링도 없어서, 마우스가 없으면 게임 자체가 불가능했습니다.

- 조작 요소는 전부 `<button>`. `<div onclick>` 금지.
- `:focus-visible` 아웃라인 필수.
- `prefers-reduced-motion: reduce`에서 전환을 즉시 끝냅니다(현재 `--dur: 1ms`).
  새 애니메이션도 이 토큰을 타야 합니다.
- 색만으로 정보를 전달하지 않습니다 (마피아/시민, 생존/사망 모두 텍스트 병기).

**파일을 늘리지 마세요.** 예전엔 11개였는데 그중 직업 카드 7개가
`background-image` URL 한 줄만 다른 같은 파일이었습니다. 직업이 12종이 되면
카드도 12개가 되는 구조였죠. 지금은 **화면의 종류만큼만** 있고, 같은 화면의
다른 내용은 파일이 아니라 payload로 전달합니다. 이 원칙을 지켜 주세요.

### 3-2. 디자인 시스템 (`src/ui/theme.css`)

빌드가 모든 위젯에 인라인하는 단일 출처입니다.

> **실제 사고:** 예전엔 위젯 11개가 각자 CSS를 처음부터 다시 썼습니다.
> 같은 의미의 색이 파일마다 다른 값이었고(#484848 / #333333 / #3c3030 /
> #563d3d … 총 26종), 타이머 글꼴이 화면마다 20px·35px·18px이었습니다.
> 한 화면의 톤을 바꾸면 나머지 열 개가 어긋났습니다.

현재 토큰:

```css
/* 표면 */  --bg:#14100f  --surface:#201a19  --surface-2:#2d2523
            --surface-3:#3b312e  --line:#4a3d39
/* 글자 */  --ink:#f5efe9  --ink-2:#b9aaa2  --ink-3:#7d6e68
/* 진영 */  --mafia:#e04b4b  --mafia-dim:#6d2424
            --citizen:#57a8e0  --citizen-dim:#24475f
/* 의미 */  --accent:#e0b355  --ok:#5fbf7f  --warn:#e0b355
            --danger:#e04b4b  --dead:#5a4a45
/* 간격 */  --s1:4px --s2:8px --s3:12px --s4:16px --s5:24px
/* 활자 */  --t-xs ~ --t-2xl  (전부 clamp(최소, vw, 최대))
/* 모서리 */ --r1:6px --r2:10px --r3:14px
/* 기타 */  --shadow  --dur:160ms  --ease:cubic-bezier(.2,0,.2,1)
```

공통 컴포넌트: `.panel`(모든 위젯의 껍데기) / `.hd`(머리말) / 타이머(링 + 남은 초,
마지막 10초·3초에 단계적 강조) / 진행률 막대 / `.btn` 계열 / `.chip`(직업 표시).

**활자가 전부 `clamp(px, vw, px)`인 이유:** 위젯 폭이 96%든 400px든 같은
컴포넌트가 뜨기 때문입니다. 고정 px로 되돌리지 마세요.

### 3-3. 공유 스크립트 (`src/ui/shared.js`)

```js
esc(v)              // HTML 이스케이프
html`<b>${x}</b>`   // 태그드 템플릿 — 보간값 자동 이스케이프, 배열은 join
Html(text)          // 이스케이프하지 않겠다는 명시적 표시
flag(on, "class")   // 조건부 클래스
qs(sel) / qsa(sel)  // 선택자
startTimer(el, sec) // 타이머 (링 + 마지막 10초/3초 연출 포함)
scrollToEnd(el)     // 채팅 스크롤
```

**타이머를 다시 구현하지 마세요.** 예전에 4개 파일이 `toHHMMSS`를 각자 갖고
있었고 90초를 "00:01:30"으로 표시했습니다 — 시(時) 자리는 이 게임에서 영원히 00입니다.

**이 계약은 서버 로직과 맞물려 있습니다. 이름과 필드를 바꾸지 마세요.**
새 필드가 필요하면 산출물에 "서버에 이 필드를 추가해 달라"고 명시하세요.
`layout` 필드는 모든 메시지에 자동으로 실려 오며 공유 스크립트가 처리합니다 —
위젯 코드에서 건드리지 마세요.

### 3-5. 빌드와 검증

```
src/ui/*.html   ← 원본 (여기를 편집)
      ↓ tools/build-widgets.js  (theme.css·shared.js·bridge.js 인라인, 주석 제거)
res/*.html      ← 산출물 (자기완결, 커밋됨)
      ↓ tools/check-widgets.js
        각 res/*.html의 <script>를 실제로 실행하고 서버처럼 payload를 던져 넣음
```

검증 명령:

```bash
npm run check:ui
```

> **실제 사고:** 빌드 스크립트가 `String.replace`의 치환 지시자(`$$`) 때문에
> `function $$`를 `function $`로 바꿔 내보냈고, 산출물에서 `$`가 두 번 정의돼
> 모든 위젯의 `$()`가 엘리먼트 대신 배열을 돌려줬습니다. type-check·lint·test·
> build가 **전부 통과**했고, ZEP에 올려 게임을 켠 사람이 콘솔을 보고서야
> 알았습니다. 빠져 있던 건 "산출물을 한 번 열어본다"는 단계 하나뿐이었습니다.

새 화면·새 상태를 만들면 `tools/widget-scenes.js`에 그 상태의 payload 장면을
추가해야 합니다 (현재 위젯 10개에 장면 43개). 검사기가 모든 `res/*.html`에
장면 최소 1개를 요구합니다.

## 4. 당신이 할 일

### 자유롭게 바꿔도 되는 것

- 시각 언어 전부 — 팔레트, 활자 스케일, 여백 리듬, 모서리, 그림자, 질감
- 각 화면의 레이아웃과 정보 위계
- 컴포넌트 구조 (새 공통 컴포넌트를 `theme.css`에 추가하는 것 환영)
- 마이크로 인터랙션과 상태 전환 연출 (CSS만, `--dur`/`--ease` 토큰 경유)
- 단계 전환 컷(`cut.html`)의 연출 — 여기는 화면을 다 쓸 수 있는 유일한 자리
- 위젯 크기 상수 (단, 세로 예산 계산을 함께 제출)

### 바꾸면 안 되는 것

- 위젯 파일 10종의 구성 (늘리지도 합치지도 않기)
- 서버 ↔ 위젯 메시지 이름과 필드
- `layout` 자동 적용 흐름 (위젯이 스스로 크기 정하지 않기)
- `<button>` 사용, focus-visible, reduced-motion 대응
- 외부 호스트 의존 없음
- `bridge.js`를 우회한 부모 창 접근

### 산출물

1. **디자인 방향 요약** — 톤, 팔레트, 활자, 근거. 현재와 무엇이 왜 달라지는지.
2. **화면별 시안** — 위젯 10종 각각에 대해:
   - 데스크톱과 모바일 두 상태
   - 주요 상태 변화 (예: 투표 전/투표 후/개표, 채팅 접힘/펼침, 생존/사망)
   - **모바일 세로 % 와 세로 예산 계산**
3. **`theme.css` 개정안** — 토큰 표와 공통 컴포넌트 CSS
4. **위젯별 HTML/CSS** — `src/ui/*.html` 형식 그대로. 기존 스크립트 로직과
   선택자 ID는 유지하고, 바꿔야 한다면 어디를 왜 바꾸는지 명시
5. **서버 쪽 변경 요청 목록** — 크기 상수, 새 payload 필드 등
6. **접근성 체크** — 대비비, 포커스 순서, 색 외 정보 전달

### 검토 기준

이 순서로 봅니다:

1. 모바일에서 게임 화면이 48% 이상 남는가
2. 처음 하는 사람이 "지금 뭘 해야 하는가"를 3초 안에 아는가
3. 자기 직업과 남은 시간이 항상 보이는가
4. 밤의 긴장과 낮의 소란이 시각적으로 구분되는가
5. 21개 직업이 24개가 되어도 구조가 버티는가
6. 위 제약을 하나도 어기지 않았는가

## 5. 흔한 실패 방식 (전부 이 프로젝트에서 실제로 있었던 일)

- 가로만 반응형으로 만들고 세로를 픽셀로 남긴다 → 모바일에서 화면 85%를 덮는다
- 예쁜 웹폰트를 쓴다 → FOUT, 사내망에서 영영 로드 안 됨, 빌드 실패
- 아이콘 폰트를 넣는다 → 아이콘 0개 쓰면서 70KB를 매번 받는다
- 화면마다 색을 새로 정한다 → 같은 의미의 색이 26종이 된다
- `<div onclick>`으로 버튼을 만든다 → 키보드 사용자가 게임을 못 한다
- 배경 이미지 위에 `position:absolute`로 글자를 얹는다 → 폭이 바뀌면
  글자가 그림 밖으로 밀려난다 (이래서 지금 배경이 CSS 그라디언트입니다)
- 입력 후 포커스를 놓지 않는다 → 플레이어 아바타가 움직이지 않는다
- 같은 화면의 변형마다 파일을 새로 만든다 → 직업 수만큼 파일이 늘어난다
